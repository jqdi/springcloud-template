## 1. Requirements (Context)

- **Goal**: 为 springcloud-template 项目实现灰度流量路由能力，支持按规则（请求头/用户白名单/百分比）将流量路由到指定版本服务实例，用于生产环境灰度发布与金丝雀发布。
- **In-Scope**:
  - 网关层（gateway）：流量染色 GlobalFilter + 灰度 LoadBalancer
  - 框架层（framework）：Feign 拦截器透传灰度标识 + 灰度 LoadBalancer（用于服务间调用）
  - 配置：`application-gray.yml` + 环境开关
  - 服务实例 metadata 注册规范：`version`/`weight`
  - 与现有 developer 模块互斥共存
- **Out-of-Scope**:
  - MQ 异步消息灰度透传（后续扩展）
  - 影子库/影子表路由（数据库隔离，独立课题）
  - 灰度监控大盘与告警（运维侧，独立课题）
  - Kubernetes Service 级灰度（本项目基于 Eureka/Nacos）

## 2. Research Findings

### 2.1 事实与约束

**代码事实**:
1. developer 模块存在于 `gateway` 和 `framework` 两个包，结构完全镜像，仅包名不同
2. `DeveloperLoadbalancer` 继承 `RoundRobinLoadBalancer`，重写 `choose()` 方法
3. 核心算法：`groupingBy(serverOrder)` → `min(order)` 取最高组 → 组内轮询
4. 策略链由 `ServicePriorityPolicy` 接口 + 4 个实现组成，按 `getOrder()` 排序
5. 配置开关 `developer.enabled`，prod 环境关闭
6. metadata 注册：Eureka `metadata-map.developer` / Nacos `metadata.developer`，当前默认注释

**业界事实**:
1. 灰度路由三层架构是业界共识（字节/阿里/美团/火山引擎均采用）
2. metadata 字段 `version` 是 Nacos 社区与阿里 MSE 标准
3. 字节泳道模式用 `X-LANE-CODE` 头 + `metadata.LANE_CODE`，强调不跨泳道
4. Spring Cloud LoadBalancer 自定义灰度策略是主流实现路径
5. Feign `RequestInterceptor` 是透传灰度标识的标准方式

**约束**:
1. `@LoadBalancerClients(defaultConfiguration=...)` 同一服务只能有一个生效 → developer 与 gray 必须互斥
2. Spring Cloud LoadBalancer 的 `RoundRobinLoadBalancer` 是基类，灰度 LB 应继承它
3. 项目已支持 Eureka 和 Nacos 双注册中心，metadata 机制需兼容两者
4. 配置中心已有热更新机制（Apollo/Nacos），灰度规则应支持动态刷新

### 2.2 风险与不确定项

**风险**:
1. `@LoadBalancerClients` 冲突：若 developer 与 gray 同时启用，Bean 注册报错。缓解：严格 `@ConditionalOnProperty` 互斥 + 文档警告
2. Feign 透传丢失：服务间调用若不透传灰度头，第二跳即串流。缓解：GrayFeignInterceptor 强制透传
3. metadata 缺失：所有实例未配置 version 时，灰度退化为轮询。缓解：fallback 到基线实例
4. 权重灰度算法不兼容：现有分组取最高不支持加权随机。缓解：独立 GrayWeightStrategy
5. 配置热更新延迟：修改灰度规则后 LB 缓存未刷新。缓解：复用现有 LoadBalancerCacheManager 刷新机制

**不确定项**:
- 见 §0 Open Questions（metadata 命名、framework 层范围、灰度模式、MQ 透传）

## 3. Innovate (Optional: Options & Decision)

### 设计点 1: 染色规则配置形式

#### Option A: YAML 静态配置
- 规则写死在 `application-gray.yml`，依赖 Spring Cloud Config 热刷新
- Pros: 简单，与现有 developer 模块风格一致
- Cons: 修改规则需重启或依赖配置文件级热刷新，不够灵活

#### Option B: 配置中心动态 JSON
- 灰度规则以 JSON 存 Nacos/Apollo，监听变更实时生效
- Pros: 运行时动态调规则，业界惯例
- Cons: 需额外监听逻辑，规则解析复杂

#### Option C: 混合模式（推荐）
- YAML 管 `gray.enabled`/`gray.headers`/模式开关等基础配置
- 配置中心存染色规则列表 JSON，通过现有 [EnvironmentChangeListener](file:///d:/code/springcloud-template/gateway/src/main/java/com/company/gateway/config/nacos/EnvironmentChangeListener.java) / Apollo 机制监听刷新
- Pros: 兼顾简单与灵活，复用项目已有热更新基础设施
- Cons: 两处配置需协调（影响小）

### Decision 1
- Selected: **Option C 混合模式**
- Why: 复用项目已有的 Nacos/Apollo 热更新机制，基础配置静态化（稳定），染色规则动态化（灵活）

---

### 设计点 2: GrayStrategy 接口设计

#### Option A: 新建独立 `GrayStrategy` 接口（推荐）
- 灰度用独立策略接口，与 developer 的 `ServicePriorityPolicy` 解耦
- Pros: 职责清晰，灰度的"泳道隔离 fallback"语义不被 developer 的"优先级分组"语义扭曲
- Cons: 两套策略接口，概念有重叠

#### Option B: 扩展 `ServicePriorityPolicy` 接口
- 复用现有接口和 `ServicePriorityPolicyManager`
- Pros: 复用现有代码
- Cons: developer 的 `support()` 返回 boolean 用于分组，灰度需要 fallback 语义（无匹配→基线），强行复用会让接口变臃肿，且 `serverOrder` 分组号语义不适用于权重随机

### Decision 2
- Selected: **Option A 新建独立 GrayStrategy 接口**
- Why: 语义不同（优先级分组 vs 泳道隔离+权重），强行复用会扭曲接口设计；独立接口更清晰

---

### 设计点 3: 权重选择算法

#### Option A: 简单加权随机（推荐）
- 计算 `totalWeight`，`Random[0, totalWeight)` 落在哪个实例区间选哪个
- Pros: 实现简单，O(n) 一次随机
- Cons: 短时间内分布可能不均

#### Option B: 平滑加权轮询（Smooth Weighted Round-Robin，nginx 算法）
- 维护每个实例 `currentWeight`，每次选择最大 `currentWeight`，选中后减 `totalWeight`，所有实例加自身 `weight`
- Pros: 分布均匀，nginx 生产验证
- Cons: 实现稍复杂，需维护实例状态

#### Option C: 一致性哈希
- Pros: 同一请求总是到同一实例
- Cons: 灰度场景要的是流量分布不是会话保持，不适用

### Decision 3
- Selected: **Option A 简单加权随机**
- Why: 灰度场景对短时分布均匀性要求不高，简单可靠优先；后续有需求可升级为 Option B

#### GrayRuleStrategy（G5 / F5）

```java
public class GrayRuleStrategy implements GrayStrategy {
    private final AtomicInteger position;
    private final String serviceId;

    public GrayRuleStrategy(String serviceId)

    @Override
    public Response<ServiceInstance> choose(List<ServiceInstance> instances,
                                            GrayContext context,
                                            GrayProperties properties)

    /** 按 metadata.version 过滤匹配实例 */
    private List<ServiceInstance> filterByVersion(List<ServiceInstance> instances,
                                                   String version,
                                                   GrayProperties properties)

    /** 过滤基线实例(无 version metadata 或 version 为空) */
    private List<ServiceInstance> filterBaseline(List<ServiceInstance> instances,
                                                  GrayProperties properties)

    /** 组内轮询选择(复用 RoundRobin 算法) */
    private Response<ServiceInstance> roundRobin(List<ServiceInstance> instances)
}
```

**路由算法**:
```
1. reqVersion = context.getVersion()
2. if (reqVersion 为空) → return roundRobin(filterBaseline(instances))
3. matched = filterByVersion(instances, reqVersion)
4. if (matched 非空) → return roundRobin(matched)
5. if (fallbackToBaseline) → return roundRobin(filterBaseline(instances))
6. else → return EmptyResponse()
```

#### GrayDyeFilter（G9，仅 gateway）

```java
@Component
@Order(-1)  // 早于 ReactiveLoadBalancerClientFilter
@ConditionalOnProperty(name = "gray.enabled", havingValue = "true")
public class GrayDyeFilter implements GlobalFilter {

    private final GrayProperties grayProperties;

    public GrayDyeFilter(GrayProperties grayProperties)

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain)

    /** 判断请求是否命中染色规则 */

    /** 按规则类型判断是否命中 */
    private boolean matchRule(ServerHttpRequest request, GrayProperties.DyeRule rule)
}
```

**染色逻辑**:
```
1. 遍历 grayProperties.getDyeRules()
2. 对每条规则按 type 判断:
   - header: 请求头 headerName == headerValue → 命中
   - whitelist: 请求头 userHeader 的值在 userIds 列表中 → 命中
   - percent: 对请求标识(如 x-deviceid)取 hash % 100 < percent → 命中
3. 命中 → 注入 x-gray-version=rule.version 到请求头
4. 多条规则命中取第一个(优先级按配置顺序)
5. 无命中 → 不注入(走基线)
```
